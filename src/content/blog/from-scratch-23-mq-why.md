> 目标：理解同步工具调用的硬限制，明确什么场景下必须引入异步架构

---

## 背景：同步 Agent 的天花板

前面所有课程的 Agent 都是**同步执行**的：

```
用户发请求 → HTTP 连接保持打开 → Agent 执行 → 返回结果 → 连接关闭
```

这个模式在简单任务下工作得很好，但遇到以下场景就会崩溃。

---

## 同步架构的三个硬限制

### 限制一：HTTP 超时

HTTP 请求有超时限制：
- 浏览器默认：无限制，但用户会关掉页面
- Nginx/负载均衡器：通常 60~120 秒
- Serverless 函数（Vercel/AWS Lambda）：**最长 30 秒**

```
场景：Agent 需要分析 100 个文件，每个文件调用一次 LLM，每次 3 秒
总耗时：100 × 3 = 300 秒

→ 在 Serverless 环境下，30 秒就超时了
→ 用户看到 504 Gateway Timeout
→ 任务实际上还在跑，但用户已经收到错误
```

### 限制二：连接中断导致任务丢失

SSE 连接是脆弱的：
- 用户切换网络（WiFi → 4G）→ 连接断开
- 用户关掉浏览器标签页 → 连接断开
- 服务器重启 → 连接断开

```
场景：Agent 已经执行了 50 步，用户网络抖动
→ SSE 连接断开
→ 服务端的 Agent 进程被终止（因为 res.end() 会抛错）
→ 50 步的工作全部丢失
→ 用户重新发请求，从头开始
```

### 限制三：无法水平扩展

同步架构下，每个 Agent 任务都要维持一条 HTTP/SSE 长连接：

```
服务器有 4 个 CPU 核心，Node.js 单线程事件循环
同时有 100 个用户在跑 Agent 任务

→ 100 个 SSE 连接同时保持打开
→ 虽然 await LLM 响应是 I/O 等待、不占 CPU，
   但每个连接的上下文（对话历史、工具状态）都占内存
→ 当 LLM 响应密集返回时，大量回调集中执行，单线程 CPU 成为瓶颈
→ 同时，同步架构无法把任务分发到多台机器——
   因为任务和连接是绑定的，连接在哪台机器，任务就只能在哪台机器
→ 无法简单地通过"加机器"来扩展处理能力
```

> **补充说明**：Node.js 的 `await` 本身不会"占满"事件循环。I/O 等待期间主线程是空闲的。
> 真正的瓶颈在于：**内存占用**（每个连接的上下文数据）、**回调风暴**（大量 LLM 响应同时返回时的 CPU 压力）、
> 以及**任务与连接绑定**导致无法跨机器调度。

---

## 解决方案：异步架构

把"接收任务"和"执行任务"分离：

```
同步架构：
用户 ──请求──▶ 服务器（执行任务）──响应──▶ 用户
              ↑ 执行期间，连接一直保持

异步架构：
用户 ──请求──▶ 服务器（创建任务）──立刻返回 taskId──▶ 用户
                    │
                    ▼
              消息队列（存储任务）
                    │
                    ▼
              Worker（执行任务）
                    │
                    ▼
              结果存储（Redis/DB）
                    │
用户 ──轮询/WebSocket──▶ 查询结果
```

---

## 消息队列是什么？

消息队列是一个**中间人**，解耦生产者（创建任务的服务）和消费者（执行任务的 Worker）：

```
生产者（Producer）        消息队列          消费者（Consumer/Worker）
     │                      │                        │
     │── 推入任务 ──────────▶│                        │
     │                      │◀── 拉取任务 ────────────│
     │                      │                        │── 执行任务
     │                      │                        │── 存储结果
```

**核心特性**：
- **解耦**：生产者和消费者不需要同时在线
- **持久化**：任务存在队列里，即使 Worker 崩溃，任务不丢失
- **削峰**：突发的大量任务排队等待，Worker 按自己的节奏处理
- **重试**：任务失败后可以重新入队

---

## 对比：同步 vs 异步

| 维度 | 同步（SSE）| 异步（消息队列）|
|------|-----------|----------------|
| **适合任务时长** | < 30 秒 | 任意长度 |
| **连接中断** | 任务丢失 | 任务继续执行 |
| **水平扩展** | 困难 | 简单（加 Worker） |
| **实现复杂度** | 低 | 高 |
| **实时性** | 高（SSE 实时推送）| 中（轮询或 WebSocket）|
| **适合场景** | 对话、简单查询 | 批量处理、长任务、定时任务 |

---

## 什么时候该升级到异步？

满足以下任一条件，就应该考虑消息队列：

1. **任务耗时 > 30 秒**（超出 Serverless 限制）
2. **任务需要处理大量数据**（分析整个代码库、批量生成报告）
3. **任务需要跨多个 Agent 协作**（Orchestrator 分发给多个 Sub-Agent）
4. **任务需要在特定时间执行**（定时任务、延迟任务）
5. **需要任务优先级**（VIP 用户的任务优先处理）

---

## 知识点总结

| 概念 | 说明 |
|------|------|
| **HTTP 超时** | 同步架构的硬限制，Serverless 环境最长 30 秒 |
| **连接中断** | SSE 连接断开会导致同步任务丢失 |
| **消息队列** | 解耦生产者和消费者的中间件，任务持久化存储 |
| **生产者/消费者** | 创建任务的服务 vs 执行任务的 Worker |
| **削峰** | 突发流量排队，Worker 按节奏处理，避免系统过载 |
