## 二、完整答题卡

### 2.1 会话存在哪——Redis
- 会话元数据、最近 N 轮、临时状态 → **Redis**。`HSET` 存字段,`EXPIRE` 定 TTL(会话超时即过期,天然处理"过期会话")。
- 别把太重的东西堆 Redis(内存),大数据放别处。

### 2.2 上下文太大怎么截
在 **token 预算**内做：
1. **滑动窗口裁剪(trim)**：从最旧砍到只剩最近 N 条 —— 简单零开销,但旧信息丢。
2. **摘要压缩(compress)**：把超窗口的旧消息用模型总结成一段摘要,替换原始消息 —— 保留信息但有一次性模型调用开销(时间+费用)。
3. 超长转 **检索式**(RAG)：长对话不能无脑塞全部 history,切到检索式问答(与第9课嵌入链路配合)。

**两个工程彩蛋(实弹亮点)：**
- **maxMessages 必须偶数**：messages 是 user/assistant 成对出现,砍成奇数会出现开头是 assistant,模型困惑"谁先说话"。
- **摘要用第三人称**：摘要是"旁白"不是"对话",第一人称会角色混乱(`"我问了…你答了…"`有歧义;`"用户询问了…AI 回答了…"`清晰)。

### 2.3 多实例部署时状态怎么共享
- **不能只靠 sticky session**(扩容/漂移/故障切换会"失忆"),必须**把会话态外部化到 Redis**(态不进实例)。
- 多实例读同一份 Redis 即共享;要**实时通知其他实例**,用 Redis Pub/Sub 或轻量 coordinator 广播。
- 多实例并发操作同一会话要加锁(见第45题),防两个任务并发覆盖字段。

## 五、追问 Q&A

**Q1：上下文超了，为什么用摘要而不是无脑滑窗？**
A：滑窗会把早期关键信息永久丢弃,长任务/决策场景经不起丢;摘要用一次模型调用把旧信息浓缩成"预设密钥"保留下,配合裁窗保住近期的完整对话。两者按场景取舍(第8课对比表)。

**Q2：maxMessages 为什么必须偶数？**
A：messages 的 user/assistant 是成对的,砍成奇数会导致开头是 assistant,模型不知道"谁先开口",生成质量下降。

**Q3：摘要为什么用第三人称？**
A：摘要是"旁白"不是"对话"。第一人称放进 user 消息里会有歧义("我/你"指谁不清楚),第三人称无论谁读都清楚角色关系。

**Q4：多实例怎么共享一个会话？**
A：会话态放 Redis(不带实例),所有实例读同一份;状态变更用 pub/sub(或 coordinator)广播,保证各实例看到一致。Sticky 只算辅助,不能作唯一保证。

## 六、避坑

- 别只说"用 Redis 存会话"就停,把 `HSET + EXPIRE` 和"为什么外置不等于 sticky"讲出来。
- 上下文裁剪一定要带偶数 + 第三人称两个细节,这是课程给你的差异化亮点。
- 别在多实例问题上只说 Redis,要说"外部化 + 广播一致性 + 并发加锁"三件套。
