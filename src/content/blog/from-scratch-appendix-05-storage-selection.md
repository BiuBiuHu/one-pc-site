## 一、30 秒版

> "我的存储按数据类型分三类：**向量**(embedding / RAG)放向量库做语义召回(第18课)；**关系型**(用户、任务、会话元数据,要 join + 事务)放关系库；**KV/Redis** 放热会话、缓存、锁、计数。检索链路是**查 → Redis 缓存 → 关系/核心 KV → 向量库(recall → rerank)**——慢查询先命中缓存层,不下沉;向量检索先读出粗候选再重排,把高开销查询控制在小范围。"

---

## 二、完整答题卡

### 2.1 各类数据放哪
| 数据类型 | 推荐存储 | 理由 |
|---|---|---|
| 向量(embedding、RAG) | 向量库(Milvus/FAISS/qdrant/pgvector) | 语义检索,支持 ANN |
| 关系数据(用户、任务、订单、会话索引,要 join/事务) | 关系库(MySQL/PG) | 强事务、一致性、join |
| KV/即时状态(会话态、token、锁、计数、队列) | Redis | 低延迟、TTL、原子操作 |

**选型原则**:不是"一款存打天下",按**数据的访问模式 + 一致性要求**分:
- 要事务/Join → 关系库;
- 要语义召回 → 向量库;
- 要极低延迟的热数据 → KV(Redis);
- 能容忍结构化的实时一致的业务元数据 → 关系库(或 KV + 关系库分工)。

### 2.2 检索慢先查哪一层（缓存分层）
```
查 → (1) Redis 缓存 → (2) 关系库 / 核心KV → (3) 向量库（语义检索，recall → rerank）
```
- **先查缓存层**,命中就下沉,降低关系库/向量库压力。
- **关系库**负责精确查询/事务;**向量库**只在语义/召回时去,并且**先 recall 出粗候选再 rerank**,控制高成本查询。
- 面试官"检索慢了先查哪一层"就是要你说出这条"缓存优先 + 分层下沉"的取舍。

### 2.3 向量/关系/KV 具体的边界
- 第18课的**离线建库**(chunk+embed)与**在线检索**(余弦 topK)是向量库的心智;生产把 SimpleVectorStore 换 Chars/Pinecone/pgvector。
- 第9课的**长期记忆**走 embedding(向量层),短期走 Redis/关系(会话)。
- 第24/26课的 **Redis** 是 KV/队列的上层设备(任务队列 LPUSH/BRPOP、进度 Hash)。

## 四、课程盲区（面试会深挖，必须补）

1. **关系库(MySQL/PG)的系统性选型**:课程基本用文件系统(38课 `.json`)+内存 VectorStore(RAG)——没有专门一门"关系 vs KV vs 向量"对照选型。要补"关系库管事务性元数据"那一格。
2. **缓存分层检索链**:课程有缓存心智 + token 控但没明说"查→缓存→关系→向量(recall→rerank)"这条链。补。
3. **向量检索成本**:第18课优化表提了"topK 再到重排",把它升级成"recall→rerank 控成本"的面试话术。

## 五、追问 Q&A

**Q1：为什么数据不都放 Redis？**
A：Redis 是内存KV,擅长热态缓存与低延迟,但不适合事务/join/以及大语义检索。关系库保证一致性和结构化查询,向量库负责语义召回——各放各的才不单点堆负担。

**Q2：RAG 检索不准，你怎么优化？**
A：先看切片太短/太长(第18课);检索不准用 HyDE(先让 LLM 生成假设答案再检索)或更大 top-K;结果重复用 MMR 保多样性;生产把小 top-K 增加。再多用 rerank 提升精确度。

**Q3：检索慢了先查哪一层？**
A：先查 Redis 缓存,命中即回;未命中下沉到关系/KV 精确查;只有语义需求才走向量检索,且先 recall 出粗候选再 rerank,把高开销限制在小范围。分层 = 用缓存换成单价低的查询。

**Q4：会话、记忆、向量各存什么？**
A：短期会话态放 Redis(第8/44),长期记忆/知识库放向量库做语义召回(第9/18),任务/业务元数据放关系库。三类互不替代。

## 六、避坑

- 别只答"我有向量库 + Redis",要讲清"为什么关系库的格不能省略"以及检索分层链。
- 向量查询别只说"搜索",要带 `recall → rerank` 的成本意识。
- 你的课程"上一生产把 JSON checkpoint/内存 VectorStore 换成正式存储"这个落地产物很真实,面试时主动说出来加分。
