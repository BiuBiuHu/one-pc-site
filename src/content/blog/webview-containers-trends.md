## 1 · 容器家族全景：把本系列所学迁移到其它的"壳"

### 1.1 问题引入

把一段在自家 App 里跑得很好的 H5 三件套——`bridge.getLocation()` 调原生、`document.cookie` 取登录态、`fetch` 发接口——原样搬进别处：塞进小程序报 "`wx.getLocation` 未授权，且没有 `document`"；搬进 React Native 直接没有 `document` 可言；放进 Flutter 页面里，H5 只是万丈 Dart 中的一个小控件，回调回来的不是 Promise 而是另一套异步消息。**知识没作废，是"壳"换了一套答案。** 本节把本系列十一个阶段沉淀下来的问题域，沿"容器光谱"逐个壳迁移。

### 1.2 先破误区

> • 误区：容器技术五花八门（小程序 / RN / Flutter / Electron…），等于每套都要从零重学一遍。
> • 事实：它们回答的是同一组问题：① 执行环境是谁（有没有 DOM、JS 引擎是什么）？② 请求走哪条网络栈？③ 页面跟宿主用什么通道通信？④ 能力边界谁定（规范 or 平台）？每家只是给出不同答案。学会"带着四问看新壳"，迁移成本远小于重学。

> • 误区："小程序就是套壳 WebView，React Native 的 WebView 用法也一样。"
> • 事实：小程序是双线程模型——业务 JS 根本不在你看到的那张渲染页里跑；RN 则是 JS 引擎驱动原生组件，WebView 在 RN 里反而只是众多原生组件中的一个。把"壳"混为一谈，排查问题时方向全错。

### 1.3 原理讲解：沿光谱逐个壳看

![容器光谱：从像浏览器到像原生](/images/webview-and-native/stage11-01-container-spectrum.png)


#### 1.3.1 小程序：双线程 + setData 桥

承接阶段 7 的容器演进三段论（单页 → 多标签 → 小程序式容器，stage-7 · 05）：小程序把"壳调度"推到极致——**逻辑层**是一个独立的 JS 上下文（iOS 上就是另一个 JavaScriptCore 实例），跑你的业务代码；**渲染层**是一个（或按页面池化的几个）WebView，只负责拿数据画视图。两边隔离，改 DOM 这条路在物理上不存在，数据变更只能通过 `setData` 过桥，由渲染层差量更新上屏。

再看 `wx.*`：它本质就是阶段 4 桥模型里的**桥 API 表**——平台下发一份能力清单（哪些 API、什么版本可用，对应"能力协商与版本"一节），每个调用打包成方法名 + 参数的信封发到宿主侧执行，再按回调对回来；`wx.login` 拿 code、`wx.request` 走平台代发的请求，与 H5 容器里"请求被壳接管"是同一件事的更彻底版本。**前端连 fetch 的自由都被收走了，换来的是壳对异常、性能、安全的全面接管。**

🧭 **对接前端的心智变化**：没有 DOM、没有 `window` 意义上的全局（只有模拟层）、没有 Cookie；生命周期换成 App/Page 组件钩子；调试器是平台家的定制面板。"双网络栈"问题的答案是"只有一条"——平台统一收口。

#### 1.3.2 React Native：JS 引擎 + 原生组件

RN 走另一条路：业务 JS 跑在集成进 App 的 JS 引擎里（Hermes 等），但**渲染不走 WebView**——JSX 里的 `<View>`/`<Text>` 被映射成原生控件（新架构 Fabric 下组件树以序列化状态同步，边界仍然是异步的消息管道与序列化数据）。因为根本没有 WebView，自然**没有 document、没有 Cookie、没有 CSS 级联**——样式是 JS 对象映射到原生布局属性，存储是平台 API（Keychain/SharedPreferences 包装）而非 localStorage。

但桥的心智模型完全可迁移：阶段 4 说"桥 = 通道 + 协议"，RN 里通道是 JS↔Native 的异步序列化消息，协议是模块方法的注册表与参数编码。**"把桥调用当异步消息、管理回调 ID 与超时"的纪律，在 RN 里原封不动成立。**

🧭 **对接前端的心智变化**：无 document / 无 cookie / 样式非 CSS；组件即原生控件，性能问题从"渲染管线"换成"桥的序列化频次"；嵌一页 H5 时，WebView 是显式引入的组件（RN 的 WebView 组件），它内部的双网络栈、Cookie 竞态问题又全线回归——套娃但层次分得清。

#### 1.3.3 Flutter：自绘引擎里的内嵌 WebView

Flutter 用 Dart 写业务，界面由自绘引擎（Skia/Impeller）直接画出来，**不经过系统 WebView，也不经过原生控件系统**。所以"嵌 H5"是显式动作：引入 `webview` widget，内部装的才是一部真正的系统内核（Android 上 Android WebView、iOS 上 WKWebView）。

Flutter 与宿主的交互走 **platform channel**：Dart 侧调方法 → 编解码为二进制消息 → 原生侧 handler 执行 → 结果异步回传。对照阶段 4：**信封、异步、按调用对回——模式与 JSBridge 神似**，只是换了编解码与语言。而那个内嵌 WebView 里的 H5 与 Flutter 页面之间再通信，还要再架一层 JSBridge 或 JS-Dart channel，等于"桥上加桥"。

🧭 **对接前端的心智变化**：你的 H5 是自绘满屏里的一个嵌入式矩形，视口、触摸、键盘事件都先被 Flutter 接走再下发；Cookie/存储问题（302 竞态、三套 Cookie）在 widget 内照旧，但登录态的"源头"在 Dart 侧，同步动作要由壳代码做——你负责把它写进需求单。

#### 1.3.4 Electron / Tauri：桌面上把浏览器当容器

桌面端把本系列的主线演成了镜像：**Electron = Chromium + Node**。每个窗口是一个 Chromium 渲染环境（完整 DOM），主进程是 Node 运行时，preload 脚本经 `contextBridge` 暴露受控 API——这就是阶段 4 里"注入桥 + 白名单"的桌面版。**Tauri = 系统 WebView + Rust 核心**：Windows 用 WebView2、macOS 用 WKWebView、Linux 用 WebKitGTK，前端 standard web 代码，命令经 IPC 进 Rust。注意 Tauri 在三大平台用的是**三种不同内核**——阶段 1 讲的内核谱系直接决定了你的兼容面。

🧭 **对接前端的心智变化**：窗口即容器、没有"页面被壳回收"之忧，但 Chromium 版本由 Electron 版本决定（自控内核的代价与收益都在）；`fetch` 依旧走 Chromium netstack（管道二），Node 主进程的请求才是"管道一"——双网络栈在桌面上重逢。Tauri 侧则要按内核逐平台实测。

#### 1.3.5 游戏内 WebView：一句带过

游戏引擎画面之上叠一层 H5 浮层时，WebView 往往架在贴于渲染画面之上的原生视图/表面，要留意三件事：透明背景与引擎渲染共存、进出浮层的生命周期由游戏自己控制、原生能力几乎全靠游戏侧自定义桥——本系列的"桥 + 容器契约"框架照用，无新知识。

### 1.5 容器光谱：一张图收束全系列

把上方光谱图读成一条结论：**越左越像浏览器（Web 规范是契约，行为可预测），越右越像原生（平台 API 是契约，行为由宿主决定）。** 光谱不是评价好坏，而是回答"我该带着哪种心智进场"：

| 光谱位置 | 你的默认假设 |
|---|---|
| 系统浏览器 / Electron | Web 规范基本兑现，少数能力受宿主裁剪 |
| WebView 容器 | 规范 + 容器契约双层，容器说了算的那层要逐项确认 |
| 小程序 / Flutter / RN | 平台契约优先，Web 常识仅存于"嵌 H5 的那一小块" |

而无论落在哪个位置，本系列四个结论不换壳地成立：**请求归发起方的栈管、桥 = 通道 + 协议、先拿容器契约再写代码、吃不准以实测为准。**

### 1.6 坑点清单

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| 拿 H5 心智写小程序 | 用 `document.cookie` 传登录态，全空 | 双线程模型无 DOM，逻辑层跑在隔离上下文 | 登录/存储走平台 API（如 `wx.setStorage` 这类存储接口），过壳不绕壳 |
| 把 RN 桥当同步函数 | 取值拿到 undefined 或 Promise 不 resolve | JS↔Native 是异步序列化消息 | 按回调/Promise 组织，注意第 4 节的回调纪律 |
| Flutter 里找不到页面 | H5 全屏白页、键盘顶不起 | WebView 是 widget，触摸事件先被 Flutter 收 | 按 `webview` 文档配置手势/键盘，别当独立页调 |
| 桌面只测一个平台 | Tauri 在 Windows 正常、macOS 乱 | 三平台三种系统内核 | 按内核谱系分平台实测，别押 Web 一致性 |
| 新壳直接抄 WebView 优化 | 离线包/预热池手段用不上 | 壳不同，容器能力清单不同 | 先问四问（执行环境/网络栈/通道/边界），再谈优化 |

## 2 · 趋势与前沿：Web 能力在容器里，以及自研内核与大厂方向

### 2.1 问题引入

同一段 H5，在桌面 Chrome 里能用的能力，落地到某壳的 iOS/Android 上可能被静默裁剪；而各厂一点一点把内核换成了自研，公开资料却几乎不答疑"为什么非换不可"。前端站在容器门口，想知道：**WebAssembly/WebGPU 在自家目标容器里到底能不能用、PWA 在 App 里还剩什么、为什么大厂宁可背内核迭代的债也要自研。**

### 2.2 先破误区

> • 误区："Safari 删了 WebGPU" / "现在 Web 能力已经很跟手了"——能力结论可以百度到、写进代码。
> • 事实：能力可用性随内核、系统版本、App-Bound 等策略动态变化，一句话的结论既快也过期。本系列红线（AUTHORING-GUIDE §2.6）同样适用于前沿能力：吃不准就实测，给一段探测代码，比抄一句二手结论可靠。

> • 误区：PWA 就是"把网页加个快捷方式"，App 里装个 Chrome 也一样能用。
> • 事实：PWA 依赖 Service Worker、安装 UI、离线缓存、推送等浏览器平台能力，而这些在 WebView 容器里根本不是"浏览器式"的——容器决定 PWA 相关能力被显式提供还是裁剪（iOS WKWebView 的 SW 受 App-Bound Domains 等策略约束，见 stage-5 · 04）。

### 2.3 原理讲解

#### 2.3.1 能力现状：以探测为准，给代码思路

三个前沿能力在容器里的现实，逐一说清"为什么不能背结论"：

**① WebAssembly。** Chromium 系（Android System WebView）对 Wasm 支持较早且较全；iOS WKWebView 近年也已支持主流 Wasm。但**支持的子集、JIT 是否开启、与 App-Bound/同源策略的交互**随版本演进，没有一条"可用/不可用"的稳定结论。

**② WebGPU。** 是"以实测为准"的极端样本——桌面 Chrome 早已默认开启，iOS 上 Safari 长期只在预览开发里部分披露，Android 各家 WebView（系统 WebView、XWeb/U4 等）里何时默认开、是否受后台/内存策略影响，版本间漂移明显（以实测为准）。**正确姿势是特性检测 + 降级回 WebGL**，而不是假设"某版本 WebGPU 必在"。

**③ PWA 在 App 内。** 在系统浏览器里，PWA=「安装 → 独立窗口 → 离线 → 推送」的闭环；在 App 的 WebView 里，推送走的是**容器与系统的 Push 通道**（APNs/FCM），不是 Web Push。所以"PWA 在 App 内"要拆成两问：**Service Worker 层**（SW 能否注册/缓存/做弱网兜底，逐壳实测）与**推送层**（App 是否把系统 Push 转给了 WebView 页面、还是只给原生层用）——这两层在浏览器里天然耦合，在容器里被拆开，正是前端最该归因的地方。

**给一段探测代码思路（不背结论）：**

```javascript
// 平台：H5。进入目标壳后跑一遍，把结果打到一个对象里
async function probeCap() {
  return {
    wasm: typeof WebAssembly !== 'undefined' && WebAssembly.instantiate ? 'likely-yes' : 'likely-no',
    webgpu: typeof navigator.gpu !== 'undefined' ? 'yes' : 'no',            // WebGPU 特性检测
    gl: !!document.createElement('canvas').getContext('webgl2'),            // 降级基准
    sw: navigator.serviceWorker && navigator.serviceWorker.controller        // SW 是否注册成功
      ? 'registered' : 'none',
    secure: typeof window.isSecureContext !== 'undefined' && isSecureContext // SW/推送都要求安全上下文
  };
}
// 产线用法：把返回对象上报到监控，按「目标设备矩阵」逐条校准，绝不在代码里写死版本号分支
```

> ⚠️ 这不是"证明存在"的代码，是**探测思路**：把它挂在灰度期、跑遍目标设备矩阵，用真实数据回答"这个能力在我要支持的壳里到底占几成"，再决定"用还是降级"。**特性检测永远优先于 UA / 版本判断**（呼应 stage-2 · 05 的能力兜底）。

**④ 隐私策略收紧的传导链。** iOS 的 ATT（App 追踪透明度）与隐私清单，Android 的广告 ID 限制，作用层在**原生 App 与系统**，但对容器内 H5 产生传导：业务方要的设备级 IDFA/广告标识，在 App 权限被拒后**传不进 H5**；容器在合规上越来越倾向"不把设备级标识直接暴露给 Web 层"，改用业务 token + 浮点化的可归因标识。前端感知 = **能拿到的设备信息变少、且各壳口径不一**——把"前端能拿到的标识有哪些、各代表什么、合规边界在哪"当成又一个"以各壳文档为准"的契约，而不是写死 `deviceId`。

#### 2.3.2 为什么大厂自研内核：统一、可控、网关级优化落地

回看阶段 2 的内核谱系与阶段 6 的双网络栈，自研内核的动机由始至终只有三个词：

| 动机 | 解决什么 | 落到容器哪一环 |
|---|---|---|
| **统一** | 系统 WebView 版本碎片化、行为不一致，测试矩阵爆炸 | 一套内核 = 一套行为 = 收敛阶段的兼容成本（红线段落） |
| **可控** | 进程、网络栈、缓存、白名单、安全边界受自己调度 | 把"由 WebView 内置网络栈决定"变成"由容器决定"（呼应阶段 6 的"网络栈统一"） |
| **网关级优化落地** | HTTPDNS、统一签名、弱网优化、流量统计等只有走**自己的栈**才能真正兑现 | H5 请求"并入客户端网络库"的第三种路线，见 stage-6 · 03 |

更通用地讲，这就是上面**双网络栈**图景的终局：依靠 WebView 内置栈，H5 请求永远在"壳的掌控"之外；自研内核（或成熟内核的精细代理）是把管道二也并入统一网络层，让前端 fetch 和原生请求享受同一套网关能力。公开层面只能确认方向（腾讯 X5→XWeb、UC U4，以及"把 WebView 网络栈重写/代理到统一网络层"）——**具体机制各厂不公开，不虚构**（stage-6 · 03 红线）。对前端的意义：**"H5 的 fetch 有没有带签名、能不能吃 HTTPDNS"这种问题的答案，正在从"看运气"变成"看你们容器走了第几条路线"，你能根据容器的栈归属主动归因了——这本身就是阶段 6 之后你的新能力。**

#### 2.3.3 开源还是封闭？一个猜测，留给读者

自研内核是重资产（内核随 Chromium 迭代、合规、更新节奏全押在自己的运维上），大厂愿意背，是因为"统一 + 可控"兑换的是线上稳定性与优化杠杆；但对绝大多数团队，正确选择仍是系统 WebView + 容器策略。**这让容器同时向两个方向撕扯**：有的壳因为紧缺原生优化能力而更"封闭"（自研内核、收口能力），有的壳因为人力资源而更"开放"（拥抱系统 WebView、依赖规范）。哪个方向对你们的壳是对的，取决于团队规模与合规投入——本系列能提供的是判断框架（四问 + 归因），不是标准答案。

### 2.4 你在这个坐标系里的位置（克制说两句）

从阶段 0 的"WebView 不是浏览器"，到阶段 6 的"没有单条网络栈"，到本节的"没有单一能力结论"——你在学会的事情是：**不再把 Web 规范当成世界的契约，而是把它当成一份默认说明书，在每一个壳里重新核对。** 这个习惯，比任何单一 API 都值钱，也是跨端团队里前端相对最稀有的技能。

在"懂容器的前端"这个位置上，价值不是"会写两行脚本修白屏"，而是能给跨端治理带来一个稳定的第三视角：**当客户端说"是网络问题"、后端说"在你壳里"、测试说"机型相关"时，你能用"请求走哪条栈、桥从哪一端注入、能力在哪个内核"把争议翻译成可验证的归因。** 这份能把模糊争议落成事实清单的能力，就是你的杠杆。走到这里，本系列的教学目标已经完成——剩下的路是回到你自己的项目里，把每一节的四问跑一遍。

### 2.5 坑点清单

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| 抄二手能力结论 | WebGPU 在真机崩、Wasm 在旧 iOS 不跑 | 能力随内核/版本/策略漂移 | 特性检测 + 降级，跑目标设备矩阵 |
| 把 PWA 当整体 | 「装好了呀怎么没离线」 | 浏览器里 SW 与推送耦合，容器里被拆开 | 分 SW 层与推送层各自归因 |

<summary>参考答案（思考后再点开）</summary>

1. 可用性随内存核、系统版本、App-Bound/策略实时变化，一句话会过期；正确姿势是特性检测 + 降级为 WebGL，并跑目标设备矩阵取真实占比。

## 3 · WebView 面试题集：20 题把全系列收成答案

### 3.1 问题引入

面试官抛出"你是 H5，那讲讲 WebView 里 fetch 走哪条网络栈？"时，很多前端第一反应是"我没写过客户端，答不了"。其实本系列的知识点都能用一两句话讲清，只是没被整理成可答题的语言。本节把十一阶段的知识收成 **20 题 × 5 组**，每题一句话场景 + 3 个以内的"考官想听什么"要点，并在题末给出**来源篇目**，方便你回查原文。答案要点全部能在所引篇目里找到依据，不引入超出系列范围的冷知识。

### 3.2 先破误区

> • 误区：面试题是背出来的新东西，跟项目实践没关系。
> • 事实：下面每一题都是本系列正文里"本可以归因的场景"的浓缩——你答得上的题，就是你线上排查过的问题。把每题的"要点"翻译回一次真实 case，就是最好的复习。

### 3.3 题目

#### 3.3.1 组一 · 基础认知（1–4）

**Q1. 简述 WebView 和系统浏览器在"本质"上的区别。**
考官想听：① WebView 是嵌进 App 的系统级组件，内核由系统/厂商/宿主共同决定② 没有地址栏、多标签、独立更新的浏览器形态③ 能力边界由宿主 App 注入的桥与容器契约决定。
出处：总章、浏览器vsWebView速查表

**Q2. 为什么同样的 H5 在不同壳里（Android 系统 WebView / X5 / iOS WKWebView）表现不同？**
考官想听：① 内核谱系：Android 可能跑 Chromium 系 / X5（TBS→XWeb）/ U4② iOS 全家桶统一用 WebKit（苹果政策）③ 同一版本内也有碎片化，行为差异**以实测为准**。
出处：内核谱系、stage-2 国产内核X5与U4

**Q3. "白屏但 App 没死"是种什么故障？怎么归因？**
考官想听：① 多半是 WebContent/渲染进程被杀，App 主进程没崩② 崩溃平台无记录、前端 JS 监控也无感③ 三分法：进程被杀 ≠ App 闪退 ≠ 加载失败，各归因容器/客户端/前端网络侧。
出处：多进程与渲染进程崩溃

**Q4. 前端在"进程级故障"面前能自救吗？为什么？**
考官想听：① 很有限，崩溃时页面 JS 整个没了来不及上报② `visibilitychange`/`pageshow` 无法区分"正常回前台"与"进程死后重启"③ 白屏自愈必须由容器（客户端代码）承担。
出处：多进程与渲染进程崩溃 §3.6

#### 3.3.2 组二 · 双端原理（5–8）

**Q5. H5 里的 fetch 走哪条网络栈？能不能自动带上客户端的统一签名？**
考官想听：① 走 WebView 内置网络栈（管道二，Android=Chromium netstack / iOS=WebKit）② 默认不经过客户端 OkHttp/URLSession（管道一）③ 因此默认不享受签名/HTTPDNS/统一监控，除非容器主动接管。
出处：两条网络栈的真相

**Q6. 不实现 WKUIDelegate 的话，页面的 alert/confirm/prompt 和 target=_blank 会怎样？**
考官想听：① JS 弹窗被**静默吞掉**：不弹、不阻塞（confirm/prompt 返回值约定为"取消"，以实测为准）② target=_blank / window.open 默认既不新开也不当前打开（开新窗是 WKUIDelegate 的职责）③ `decidePolicyFor` 系列要**恰好调用一次** completionHandler。
出处：导航控制与弹窗的坑

**Q7. `addJavascriptInterface` 注入的方法跑在哪个线程？动 UI 有什么坑？**
考官想听：① 跑在名为 `JavaBridge` 的**后台线程**② 直接碰 View/UI 会出并发问题，须先切回主线程③ 返回给 JS 的仍是异步回调，不能当同步函数。
出处：stage-2 JS与Native互调

**Q8. `shouldOverrideUrlLoading` 什么时候**不**回调？靠它做总闸有何风险？**
考官想听：① 常见不回调场景：表单 POST、部分 iframe 导航、window.open（走 onCreateWindow）、页面内资源（走 shouldInterceptRequest）② 想全量拦截必须另靠 shouldInterceptRequest（资源级）③ 不能把它当"所有请求的总闸"。
出处：导航控制与URL拦截

#### 3.3.3 组三 · 桥与安全（9–13）

**Q9. 一个标准 JSBridge 调用从发起到回调，要经历哪些节点？**
考官想听：① 就绪→拼信封（参数序列化 JSON）→跨进程到原生→执行→回包→JS 按 callbackId 找到当初的 resolve② 回调丢失常源于超时/并发/回包错位，递增 id 比时间戳稳③ 桥 = 通道（系统 API）+ 协议（信封/回调池/超时）。
出处：四种通信通道对比、一次调用的完整时序

**Q10. 为什么老的 `iframe src=jsb://` URL Scheme 通道现在被废弃了？**
考官想听：① 吞吐低、连发合并、部分导航场景不回调② 与现代消息走桥（postMessage / addJavascriptInterface）相比丢消息面更大③ 仍是"历史通用/向下兼容"理解的通识，现代项目主选协议层。
出处：四种通信通道对比

**Q11. H5 登录成功后进支付，偶发 401——最可能是什么？**
考官想听：① Native 写 Cookie 后没等落盘就 loadRequest，首跳没带上② 或依赖 302 + Set-Cookie 时出现 **302 竞态**：重定向链上 Set-Cookie 还没写完存储，紧接请求没带上③ 归属 Cookie 写入时序，不是前端代码 bug。
出处：Cookie三套体系与同步、stage-3 Cookie与存储

**Q12. 桥的接口怎么做安全校验，避免任意页面都能调用原生能力？**
考官想听：① 域名白名单（scheme 白名单）为基础的边界② 签名 + token 下发的分层策略③ 结合 `@JavascriptInterface` 只暴露标注方法、以及阶段 9 的 JSBridge 安全纵深。
出处：URL 拦截与 scheme 路由 §白名单、弹窗文件权限与销毁 §安全提示

**Q13. addJavascriptInterface 的历史漏洞要提一句什么？**
考官想听：① 反射漏洞影响 API 17 之前② API 17+ 必须 `@JavascriptInterface` 注解才暴露方法（没有它方法不进 JS 的方法表）③ 现代 Android 配置安全的其它开关是 file 域、Mixed Content 等（见 WebView 配置全景）。
出处：stage-2 JS与Native互调、WebView 配置全景

#### 3.3.4 组四 · 性能与缓存（14–17）

**Q14. 白屏归因第一步该怎么分？**
考官想听：① 白屏 ≠ 加载慢≠ 进程被杀 ≠ App 闪退② 用"进程被杀 / App 闪退 / 加载失败"三分法拆归因③ 再按"启动耗时瀑布"逐段定位（WebView 创建→网络→渲染）。
出处：多进程与渲染进程崩溃 §3.4、启动耗时拆解

**Q15. 离线包 与 Service Worker 的区别是什么？**
考官想听：① 离线包 = 资源打进 App + 请求被容器拦截后映射到本地文件（壳的能力）② SW = 页面注册脚本，在 WebView 内当网络代理（Web 层能力，受内核/策略约束、以实测为准）③ 术语红线：离线包 ≠ 缓存 ≠ SW，主流秒开走离线包而非 SW。
出处：离线包的本质、ServiceWorker与离线

**Q16. 同一 H5 第二次打开快、某机型却像清了缓存——往哪归因？**
考官想听：① 可能是 HTTP 强缓存导致"版本不更新"或反之缓存策略差异（WebView CacheMode / WKWebView 缓存 API 限制）② 存储生命周期在两端不同（localStorage 清除时机 iOS 有历史坑）③ Cookie 三套体系的同步差异也要列入候选。
出处：HTTP缓存与强缓存问题、前端存储的真相

**Q17. 怎么把"点击到首屏"拆成可量化的一段段？容器侧和前端侧各占哪些？**
考官想听：① 点击→WebView 创建/复用→网络请求→渲染→首屏，各段独立归因② 预热池/离线包/模板预渲染是容器侧的占用③ FCP 在 WebView 里要按容器统一口径，别只看前端性能面板。
出处：启动耗时拆解、预热池与容器公共能力

#### 3.3.5 组五 · 排障实战（18–20）

**Q18. 线上反馈"H5 白屏"，崩溃平台无记录、JS 监控也无报错——你会怎么排？**
考官想听：① 先按三分法怀疑"进程被杀/渲染进程回收"而不是线上代码崩了② 拉宿主日志与渲染进程日志、确认是"谁先倒的"（页面崩 vs 宿主重建 WebView）③ 推动容器侧白屏探测与自动重载自愈，前端自保能力有限。
出处：多进程与渲染进程崩溃 §7、白屏诊断

**Q19. "原生接口正常、H5 接口偶发 401/超时/抓不到包"——最可能是哪一类问题？**
考官想听：① 大概率是 H5 请求走管道二、没带客户端签名/网关鉴权失败（401）② 或 HTTPDNS 只在客户端网络库，H5 享受不到（弱网/劫持明显）③ 用 UA/header/线程/是否进客户端监控区分"这条请求是哪条栈发的"。
出处：两条网络栈的真相 §3.4

**Q20. 你会怎么验证"目标机型上某个 Web 能力到底可用不可用"？**
考官想听：① 不背二手结论，用特性检测 + 降级兜底② 挂灰度期跑目标设备矩阵取真实占比（WebGPU→降级 WebGL 等）③ UA 可被改写，能力探测优先于 UA/版本判断、必要时以实测为准。
出处：国产内核X5与U4 探测、趋势与前沿 §3.1

### 3.4 结语

这 20 题的每一题，都在本系列某篇正文的"问题引入 / 先破误区 / 归因表 / 坑点清单"里有出处。答题不是背答案，而是把这些已知 case 用自己的话讲顺——**如果你能把每题要点还原成一个线上小事故，本系列就真正闭环了。**

### 3.5 坑点清单

| 坑 | 现象 | 根因 | 解法 |
|---|---|---|---|
| 背结论答两端 | iOS 与 Android 答成一套 | 忽略内核谱系与行为差异 | 每题先问"哪端、哪版本"，再答"以实测为准" |

| setData | 小程序里把数据变更从逻辑层"过桥"送到渲染层的通道，渲染层据此差量更新上屏。 |
| 桥 / JSBridge | Web 页面和原生宿主之间通信的那条通道，="通道 + 协议"（系统 API + 信封/回调）。 |
| React Native | 用 JS 写业务、渲染却走原生控件的框架，页面运行在集成进 App 的 JS 引擎里，没有 WebView。 |
| Hermes | RN 内置的 JS 引擎之一，业务 JS 就跑在它上面。 |
| Flutter | 用 Dart 自绘引擎直接画界面的框架，不经过系统 WebView，要嵌 H5 需显式引入 webview 控件。 |
| Platform Channel | Flutter 与宿主的通信通道：Dart 调方法→编解码成消息→原生执行→异步回传，和 JSBridge 神似。 |
| Electron | 桌面端"Chromium + Node"：用整套浏览器内核当窗口，Node 当主进程，属于自控内核的壳。 |
| contextBridge | Electron 的 preload 里给页面暴露受控 API 的注入机制，即"注入桥 + 白名单"的桌面版。 |
| Tauri | 桌面端用系统 WebView 当外壳、Rust 当核心的框架，三大平台各用各的系统内核。 |
| WebView2 | Tauri/Windows 场景用的系统内核（Edge 内核），是容器光谱上偏"浏览器"的一端。 |
| WKWebView | iOS/macOS 系统提供的 WebView 内核，Tauri 在 macOS 上就是用它。 |
| 容器光谱 | 把各类"壳"按"像浏览器 → 像原生"排成的一条线，用来确定你该带哪种心智进场。 |
| 双网络栈 | 壳里常见的两套请求：页面内置栈发的（管道二）与客户端网络库发的（管道一），归因时先分清。 |
| WebAssembly (Wasm) | 浏览器/WebView 里跑的"接近原生速度"的字节码，能不能用要看内核版本，以实测为准。 |
| WebGPU | 网页里调用现代 GPU 的新标准，容器里是否默认开随版本漂移，写代码要降级回 WebGL。 |
| WebGL | 上一代网页图形 API，WebGPU 用不了时的兜底选项。 |
| PWA | 让网页能"安装、离线、推送"的一套浏览器能力，进了 App 容器会被拆成 SW 层与推送层分别对待。 |
| Service Worker (SW) | 页面注册的一段后台脚本，可在 WebView 内当网络代理做离线缓存，能不能注册受内核与策略约束。 |
| App-Bound Domains | iOS 的隐私策略，限制 WKWebView 里 Service Worker 这类能力只能在指定域名下用。 |
| 特性检测 | 写代码时不猜版本，直接探测"这个能力在吗"，配上降级方案兜底，比背二手结论可靠。 |
| ATT | iOS 的"App 追踪透明度"：用户一旦拒绝，设备的广告标识符就传不进容器里的 H5。 |
| 隐私清单 | 苹果要求的 App 数据使用清单，通过它收紧"哪些设备信息能被谁拿到"。 |
| IDFA | iOS 的设备级广告标识符，被 ATT 拒绝后 H5 拿不到，得改用业务 token 类标识。 |
| APNs / FCM | iOS / Android 的官方系统推送通道，App 容器里的 H5 推送要走它而不是 Web Push。 |
| 自研内核 | 大厂把系统 WebView 换成自家维护的内核，图"统一行为 + 可控调度 + 能吃到网关级优化"。 |
| X5 / XWeb | 腾讯的国产内核系列，X5 为早期版本，后演进为 XWeb。 |
| U4 | UC/阿里系的国产内核，与 X5 同属"自研替代系统碎片化"的路线。 |
| HTTPDNS | 用 HTTP 请求直接问"该域名连哪个 IP"，绕过传统 DNS，通常只在客户端网络栈里生效。 |
| WebView | 嵌进 App 里展示网页的系统级组件，能看网页但没有地址栏，能力由宿主说了算。 |
| 内核谱系 | 各家 WebView 底层渲染引擎的家族地图（Chromium 系 / WebKit / 国产内核），决定行为差异。 |
| WKUIDelegate | iOS 里负责"弹窗、开新窗"等 UI 行为的回调对象，不实现的话 alert、window.open 会被静默吞掉。 |
| addJavascriptInterface | Android 把原生对象暴露给 JS 的注入方法，历史上漏洞多，现在必须配合注解使用。 |
| @JavascriptInterface | Android 的注解，只有标了它的方法才能被网页 JS 调到，是安全边界。 |
| shouldOverrideUrlLoading | Android 里拦截页面导航的回调，表单 POST、iframe、window.open 等场景并不会走它。 |
| shouldInterceptRequest | Android 里资源级请求拦截的回调，能拿到比导航拦截更全的请求，才能当"总闸"。 |
| JSBridge | 网页和原生之间的通信通道 + 协议：拼信封、跨进程、按 callbackId 对回结果。 |
| 管道二 / 双网络栈 | H5 里的 fetch 走 WebView 内置栈（管道二），不经过客户端 OkHttp/URLSession（管道一）。 |
| 302 竞态 | 重定向链上 Set-Cookie 还没写进存储，下一个请求就发出去了，导致偶发 401。 |
| 离线包 | 壳把静态资源提前打进 App，请求被容器拦截后直接映射到本地文件，秒开的主力手段。 |
| Service Worker | 页面注册的后台脚本，能当网络代理做离线缓存，但受内核/策略约束，逐壳实测。 |
| 三分法 | 白屏排查先分成"进程被杀 / App 闪退 / 加载失败"三种情况，各归各的因。 |
