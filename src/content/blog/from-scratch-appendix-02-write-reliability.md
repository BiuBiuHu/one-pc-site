## 一、30 秒版

> "写操作可靠 = 幂等 + 状态机 + 回滚。幂等 key 让客户端带 UUID 进幂等表去重(同 key 同 hash 返回缓存响应、同 key 异 hash 冲突 409)；重复请求由状态机挡——**completed 终态直接拒绝, 只有 pending/running 才接收**,并叠乐观锁 CAS；失败处理看错误分类(第32课):瞬时重试、永久不重试、逻辑错误交给模型重规划；回滚上用 Saga/可补偿事务,并区分'能回滚的操作'和'已产生副作用只能幂等对账'的两类。"

## 二、完整答题卡

### 2.1 幂等 key 由谁生成

| 生成方 | 时序 | 说明 |
|---|---|---|
| 客户端生成(UUID) | 调用前 | 能跨失败重试去重，但依赖客户端可信。**大部分业务首选** |
| 服务端生成 | 到达时 | 可控、防恶意，但"先落地再重试"流程变复杂 |

**幂等表结构**：存 `(幂等key, request_hash, response, status, version)`。
- 收到请求 → `lock(key)`。
- 同 key 同 hash → 直接返回缓存响应;
- **同 key 异 hash → 409 冲突,拒绝**(这是防止"同一请求被篡改重放"的关键)。

### 2.2 重复请求怎么挡
状态机驱动,不是查一张表就行:
```
PENDING → RUNNING → SUCCEEDED / FAILED / CANCELLED
```
- 终态(`SUCCEEDED`)不接受重复执行,直接挡;中间态(`PENDING/RUNNING`)才接收。
- 叠**乐观锁 version + CAS**:并发冲时序冲突的请求直接失败,不会重复执行。

### 2.3 失败了怎么回滚
写操作跨多个子步骤(如 Schedule 改了多个资源),单点失败不能把系统留在半提交:
- **Saga / 可补偿事务**:每个步骤配一个补偿(compensate)动作,失败时反序回调补偿,并记入事务日志供人工/自动化赔偿。
- **状态回滚 / Wal**:写入写在事务日志缓存,失败时反向抵消;成功后提交最终。
- ⚠️ **不可回滚的外部副作用(已发邮件/已调外部 API)只能幂等 + 对账,不能真回滚**——这是高级答案和背概念的分水岭。

## 五、追问 Q&A

**Q1：幂等 key 谁来保证唯一？客户端会不会乱传？**
A：key 由客户端生成,保证同一"业务意图"的重试带同一个 key;服务端按 key+hash 去重,hash 不同就 409。若客户端不可信,则服务端先落地再生成的 key + 乐观锁防重放。

**Q2：状态机和幂等表重复吗？**
A：不重复，两者分工：状态机定义"哪一步可重入"(completed 拒绝)、幂等表负责"同一请求的响应缓存与去重"。合起来才是完整防护。

**Q3：跨多个资源的写，怎么保证一致性？**
A：用 Saga。每个子操作配补偿动作，失败反序调用补偿；对于无法回滚的外部副作用(已发邮件)，只能靠幂等 key + 对账任务收敛。队(事务日志)保存补偿进度。

**Q4：Index 退避的 jitter 是干嘛的？**
A：防惊群。多个并发失败(比如限流)如果同时重试会再次打爆服务端；随机加个偏移(full 40ms~60ms)把它们散开。→ 直接讲第32课。

## 六、避坑

- 别把"重试"当"可靠"：重试保证的是瞬时错误的自愈，不保证幂等。面试官区分这两层。
- 状态机别只说"成功/失败"，要带上 `PENDING/RUNNING/FAILED/CANCELLED` 和 `SUCCEEDED` 到底"哪个状态拒绝重复"。
- 回滚能力强弱是加分项：一定要点出"外部副作用不能真回滚只能幂等对账"。
