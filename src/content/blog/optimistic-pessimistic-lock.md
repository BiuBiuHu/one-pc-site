> 一句话：乐观锁和悲观锁是**处理「并发写冲突」的两种相反假设**——一个假设冲突少见、更新时才校验，一个假设必然冲突、操作前先独占。

## 一、先建立直觉

两个程序员都要改订单 `id=1` 的余额：

- **悲观锁**：想起都改？先把它**锁住**，我改的时候你别碰，我放开了你再碰。
- **乐观锁**：随便你们都改，谁最后提交时发现**版本不匹配**，谁就失败重来。

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 假设 | 写冲突**频繁**，干脆提前独占 | 写冲突**罕见**，先放行、提交时校验 |
| 加锁时机 | 操作**前** | 提交/更新**时** |
| 关键词 | lock / 独占 | version / CAS(Compare-And-Swap) |

---

## 二、悲观锁（Pessimistic Lock）

核心：**先拿锁，再干活，全程独占，最后释放。** 锁的粒度决定了并发度。

### 2.1 数据库层：`SELECT ... FOR UPDATE`

```sql
BEGIN;
-- 先把要改的行锁住（排他锁），其他事务的读写都阻塞到这个事务提交
SELECT * FROM account WHERE id = 1 FOR UPDATE;
UPDATE account SET balance = balance - 100 WHERE id = 1;
COMMIT;   -- 提交后才释放锁
```

- **FOR UPDATE** = 排他锁（写锁）；**FOR SHARE** = 共享锁（读锁，可并发读）。
- 锁在**事务提交/回滚时释放**，所以悲观锁必须包在事务里，且**锁的持有时间 = 事务长度**。
- 风险：**锁持有太久 → 阻塞海量并发 → 死锁**（两个事务互相等对方释放）。

### 2.2 应用层：单机锁 与 分布式锁

| 场景 | 实现 |
|---|---|
| 单机单线程内 | `synchronized` / `ReentrantLock` |
| 单机多实例 | 进程内锁无效，要**分布式锁**：Redis `SETNX`、ZooKeeper 临时节点、数据库唯一索引行锁 |

**悲观锁通用代价**：并发低、有死锁风险、持有期间阻塞别人——适合**写多、冲突高的热点**。

## 三、乐观锁（Optimistic Lock）

核心：**不加锁，更新时用 `version` 做 CAS 校验，版本对不上就说明被人抢先改了，失败重试。**

### 3.1 典型实现：version 字段

```sql
-- 读：先取回当前 version
SELECT balance, version FROM account WHERE id = 1;   -- version = 3

-- 写：条件带上 version，且 version+1；影响行数=0 说明 version 已被别人改掉
UPDATE account
   SET balance  = balance - 100,
       version  = version + 1
 WHERE id = 1 AND version = 3;
-- 如果 affectedRows == 0 → 冲突，重试（重新读一遍再试）
```

### 3.2 其他 CAS 形态

- **数据库**：上面的 `WHERE version = old` 原子更新。
- **内存/应用**：Java `AtomicInteger.compareAndSet`、Node/C 的原子操作。
- **Redis**：`WATCH` + `EXEC`（乐观锁语义）。
- **时间戳 / 更新前后比较整行**：也能做，但**时间戳粒度粗、可能 ABA**，首选递增的 `version`。

### 3.3 乐观锁收益与代价

- **收益**：不加锁、读无并发阻塞、吞吐高、无死锁。
- **代价**：冲突时会**空交易(丢更新)**，要**重试**；大量冲突会导致重试风暴、写效率塌方。
- 适合**读多写少、冲突低**的场景。

> **ABA 问题**：如果只比「值没变」而非「版本递增」，`A→B→A` 会误判没被改过。用 `version 每次 +1`（单调递增）天然规避。

## 四、一张表对比 + 选型决策

| 维度 | 悲观锁 | 乐观锁 |
|---|---|---|
| 适用冲突频率 | 高 | 低 |
| 读写模型 | 写多 | 读多写少 |
| 并发吞吐 | 低 | 高 |
| 死锁风险 | 有 | 无 |
| 冲突处理 | 阻塞等待 | 失败重试 |
| 实现成本 | 偏高(锁/分布式锁) | 低(一行 version + 重试) |
| 锁粒度 | 表/行/记录，可粗可细 | 最小(仅更新时间) |

**决策口诀**：

- **写多、冲突高、要求强一致** → 悲观锁（如库存扣减这种热点卖超问题）。
- **读多写少、冲突低、要高吞吐** → 乐观锁（如资料简介、点赞计数）。
- 更普适的做法：**乐观为主 + 冲突重试，热点再加悲观兜底**。

## 五、细节与坑

1. **悲观锁事务要短**：锁持有时间 = 事务时间，别在事务里做外部 IO，否则锁占太久。
2. **乐观锁要幂等 + 重试**：冲突重试时不能重复扣款，重试前要幂等去重。
3. **分布式环境**：乐观锁的 CAS 依赖单行原子 UPDATE(DB 内)，跨库/跨表做不了原子 CAS，需要分布式锁或事务。
4. **锁粒度**：悲观锁尽量锁**行**别锁表，粒度越小并发越高。
5. **ABA**：乐观锁务必用**单调递增 version**，别只比时间戳。

## 六、结合 Agent 场景

| 场景 | 用哪个 |
|---|---|
| 多 Agent 同时改同一 Checkpoint 状态 | 乐观锁：`WHERE stepIndex = ? AND version = ?`，防止步骤被覆盖 |
| Redis 共享状态被多 Worker 并发写 | 乐观锁：`WATCH` + `EXEC`；高冲突再上 SETNX 分布式锁 |
| 定时任务多实例防重复执行 | 悲观锁：Redis `SETNX` 抢占，谁拿到锁谁跑 |
| 库存/余额这类热点、卖超就完蛋 | 悲观锁 `FOR UPDATE` 强一致，或乐观锁 + 严格重试 |
| Agent 写操作可靠性 | 乐观锁 version+CAS 挡并发写，「终态拒绝重复」叠状态机 |

> 一句话给 Agent 场景：**能用行级乐观锁就用乐观锁；涉及热点/跨实例强一致，再用分布式悲观锁。**

## 七、实战案例：现金贷提现（悲观锁 vs 乐观锁）

> 金融里「提现/扣款」是最典型的**读-改-写竞态**场景，用它最能看清两种锁的真差别。

### 7.1 业务设定与隐患

- 用户**可用余额 = 5000 元**，在两个设备上**同时**发起两笔提现，各提 4000。
- 规则：提现前校验 `余额 >= 提现金额`，否则拒绝（防**资金透支/超提**）。
- 隐患：两笔都「先查 5000，都觉得够 4000」→ 没保护就会**超支**——5000 被提走 8000 = 资金事故。

### 7.2 悲观锁版：先锁行再校验（FOR UPDATE）

```sql
BEGIN;
SELECT balance FROM account WHERE id = u1 FOR UPDATE;   -- ① 直接锁住该余额行
-- 业务校验：5000 >= 4000 ?
UPDATE account SET balance = balance - 4000 WHERE id = u1;
COMMIT;                                                   -- 提交才释放锁
```

| 时刻 | 提现 A（4000） | 提现 B（4000） |
|---|---|---|
| t1 | `FOR UPDATE` → **拿到行锁** | |
| t2 | | `FOR UPDATE` → ⛔ **阻塞等待**（排队） |
| t3 | 校验 5000≥4000 ✅；扣减为 1000 | ⛔ 仍被阻塞 |
| t4 | `COMMIT`（释放锁） | 放行 → 读到最新 `balance=1000` |
| t5 | | 校验 1000≥4000 ❌ **拒绝「余额不足」** |

**结果**：只有 A 成功，总提现 4000，不超 5000 ✅。B 被「**阻塞排队**」，锁从检查到 COMMIT 全程持有。

### 7.3 乐观锁版：不锁行，提交时 version 比对

```java
Account a = accountMapper.selectById(u1);   // ① 快照读，拿到 version（不加锁）
int rows = accountMapper.deductWithVersion(u1, 4000, a.getVersion());
// UPDATE account SET balance = balance - 4000, version = version + 1
//  WHERE id = u1 AND version = #{oldVersion}
if (rows == 0) {                            // ② version 对不上 = 冲突
    return retryWithOptimisticLock(u1, 4000);   // 重试
}
```

| 时刻 | 提现 A（4000） | 提现 B（4000） |
|---|---|---|
| t1 | 读 `balance=5000, version=1` | 读 `balance=5000, version=1` |
| t2 | `UPDATE ... WHERE version=1` → ✅ 影响 1 行 | `UPDATE ... WHERE version=1` → ⛔ 影响 0 行（version 已是 2） |
| t3 | commit | **检测冲突 → 重试** |
| t4 | | 重试读到 `balance=1000, version=2` → 校验 1000≥4000 ❌ **拒绝「余额不足」** |

**结果**：同样只有 A 成功 ✅。B **全程不阻塞**，只是提交时 version 对不上 → 靠重试兜底。

### 7.4 对比与金融网选型

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 提现 B 此刻在干嘛 | **阻塞排队**等 A 提交 | 照常跑，提交才发现冲突 |
| 锁持有时间 | 长（SELECT→COMMIT） | 极短（仅 UPDATE 一瞬） |
| 冲突处理 | 靠「等」 | 靠「重试」 |

**金融场景建议**（资金字段，冲突率高必须强一致）：

- 首选**单条原子 UPDATE**（最简，条件天然防超提）：

```sql
UPDATE account SET balance = balance - 4000
 WHERE id = u1 AND balance >= 4000;   -- 影响 0 行 = 余额不足
```

- 需要「读出来做复杂业务校验再扣」时用**悲观锁 FOR UPDATE**。
- **乐观锁留给低冲突字段**（用户资料/备注/状态机），资金热点别只靠它，冲突频繁会重试风暴。

> **两个常见误解（一定要纠）**：
> 1. 悲观锁 **不是**「禁止别人读」——别人仍能用快照读读到**旧版本**，只是不能改、不能抢锁。
> 2. 乐观锁 **不是**「别人不能改」——别人照常能读能改，只是最后提交时 version 比对会判出冲突、后到者失败重试。

## 八、面试速记

- 悲观锁=先锁后做(独占、阻塞、易死锁)；乐观锁=更新时校验(并发高、冲突重试)。
- 选型关键：**冲突频率 + 读写模型**。写多冲突高→悲观；读多冲突低→乐观。
- 别漏 **ABA**：乐观锁用单调递增 `version` 规避。
- 跨实例(分布式)别想在 DB 里做 CAS，用分布式锁(Redis SETNX / ZK)。
