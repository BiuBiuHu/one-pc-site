## 二、完整答题卡

### 2.1 多个 Agent 同时改同一个文件怎么加锁
- **进程内(Semaphore 信号量)**：并发控制上限,超出进入等待队列(第35课)。只对**单实例进程内**并发有效。
- **跨实例(分布式锁)**：Redis `SET key token NX PX`(NX 保证原子占位、PX 设置**租约超时**防 owner 挂掉锁不释放)。加锁粒度要落到**资源维度**(按 project/文件/路径段分锁)。
- 也可用**乐观锁替代悲观锁**：资源带 version,CAS 更新,冲突则失败/重试,比悲观锁好排查。

### 2.2 沙箱怎么隔开
> 纵深防御：三层独立,**任何一层被突破,下一层仍有效**。
```
输入 → ③ Prompt Injection 检测(进 LLM 前拦截)
        → ② 工具白名单(挂载阶段过滤,LLM 根本"看不见")
                → ① 路径沙箱(工具执行时校验路径)
```
- **路径沙箱**:`path.resolve` 展开 `..` 后校验 `startsWith(sandboxRoot + path.sep)`。**`path.sep` 必须有**——否则 `/tmp/workspace-evil` 会被误判成 `/tmp/workspace` 前缀合法。
- **工具白名单 = 最小权限**:不给 `write_file` 就物理上写不了文件(不管 LLM 多聪明)。过滤发生在挂载阶段。
- 生产差距(第14课自己列了):命令沙箱(禁 `rm -rf`/`curl|bash`)、网络沙箱(限域名 IP)、速率限制、审计日志。

### 2.3 限流/熔断在网关还是业务层（不是二选一）
| 层 | 管什么 | 例子 |
|---|---|---|
| 网关层 | 全局、跨实例、无业务语义的尖峰与并发形状 | 每 key QPS、全局并发、连接数 |
| 业务层 | 具体资源的语义限制,能区分业务异常 | 某项目 token 预算、某任务的锁冲突、某上游 LLM 配额 |
- **判断原则**:网关层不知道"上一层执行了什么"、无法做业务语义判断的部分放网关;要感知具体资源语义的放业务层。**熔断放网关注处/调用层**(依赖 LLM 库熔断)。

## 四、课程盲区（面试会深挖，必须补）

1. **跨实例分布式锁**:第35课 Semaphore 是进程内的,不是分布式。补 Redis `SET k v NX PX` + 租约(lease)以及粒度。
2. **乐观锁 / CAS**:课程第38课直接覆盖单机写,没并发写。补 version + CAS。
3. **熔断器(circuit breaker)**:课程没系统性讲熔断(集中讲了限流/配额)。补"熔断(checking)放网关/调用层、针对依赖失败率"。

## 五、追问 Q&A

**Q1：Semaphore 和分布式锁有什么区别？**
A：Semaphore 是"控制并发数"的进程内计数(第35课),分布式锁是"互斥写某资源"的跨实例能力。单机只要信号量就好,多实例并发写同一个文件必须用 Redis 分布式锁 + 租约超时防死锁。

**Q2：`SET NX PX` 里的 PX 是干嘛的？**
A：租约超时。拿到锁的进程假如崩溃/pause,没它锁永远不会释放(死锁);超时后锁自动续走,配合续约(renew)使用。

**Q3：限流放网关还是业务层？**
A：都放,分工不同:网关控流量尖峰和并发形状(全局),业务层控资源语义(哪个项目/哪个文件忙)。判断标准是"这一层是否知道上一层执行了什么"——需要语义的部分只能放业务层。

**Q4：沙箱里 Prompt Injection 检测能作为唯一防线吗？**
A：不能。正则/启发式有漏报误报(混淆、Unicode、多语言都能绕),它只是拦低成本常见攻击;真正的安全靠路径沙箱 + 工具白名单的**硬性限制**。

## 六、避坑

- 别把信号量当分布式锁:面试官追问"多实例"你就暴露了——主动补上 Redis 分布式锁。
- `path.sep` 保护细节一定要讲(前缀误判),这是课程里难得的防御细节,能拉开和背概念的人的差距。
- "限流放哪"别答"选一个",答"都放 + 分工依据"。熔断单独补。
